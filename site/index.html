shellwise

A seatbelt for AI agents in your terminal.

It reads every shell command your agent is about to run and stops the ones that won’t run, will hang, or will delete the wrong thing. In about 15 ms.

Download v0.1.0 View on GitHub

Open source (GPL-3.0) · Rust · Bash and PowerShell · Windows, Linux, macOS

The problem

Your agent runs commands you never read

A coding agent writes a shell command and runs it within the same second, hundreds of times a day. Most are fine. A wrong quote costs a retry. A loop that never ends costs a night. A delete in the wrong folder costs the work.

It won’t run

The shell will refuse it or read it differently than the agent meant.

Write-Output "$name: done"

PowerShell reads $name: as a drive.

It will hang

The command waits for something that may never come.

until grep -q done log; do sleep 15; done

No counter, no deadline.

It will destroy

A delete aimed at more than the agent thinks.

rm -rf "$DIR/"

If DIR is empty, this is rm -rf /.

What the agent sees

A reason and a fix, not just “no”

Every finding carries a Fix line the agent can copy, so it corrects itself and carries on without you.

$ shellwise check --shell bash -- 'until grep -q done build.log; do sleep 15; done'
break wait-loop-unbounded
the loop polls and nothing bounds it: no counter, deadline or timeout ends it, so when what it waits for never comes it runs forever
Fix: for i in $(seq 1 40); do grep -q done build.log && break; sleep 15; done
$ shellwise check --shell pwsh -- 'Write-Output "$name: done"'
break ps-var-colon
in a double-quoted string PowerShell reads $name: as a variable on a drive called name, and refuses the whole command
Fix: write "${name}:" instead of "$name:"

A true story from building it

One of our own agents waited 9 hours for a line in a log file that was never written.

until grep -q '^done' status.txt; do sleep 15; done

The job it was waiting for had already failed, and the loop had no way to notice. shellwise now stops this shape and offers a version with a limit.

Unknown tool? Not its business

A command shellwise has never heard of is never blocked for being unknown. No allow-list to maintain.

The shell is the judge

Where a rule says “Bash will refuse this”, a test asks real Bash. Same for PowerShell.

Silent when it agrees

An ok command produces no output at all. You see shellwise only when it has something to say.

Five answers

It speaks up in proportion to the risk

LevelWhat it meansWhat happens
okNothing to sayRuns. No output.
warnProbably fine, worth a noteRuns. The agent gets one line of advice.
breakWill fail or hang as writtenNot run. The agent gets the corrected command.
dangerMay destroy workNot run, unless repeated with # shellwise: allow at its end.
criticalSystem files, the repository itselfNever run. A human has to do it by hand.

Try it

One binary, one hook entry

Download the archive for your system from the latest release, or build it yourself:

git clone https://github.com/Borcioo/shellwise
cd shellwise
cargo build --release

Then add it to Claude Code as a PreToolUse hook in your user settings.json:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|PowerShell",
        "hooks": [
          { "type": "command", "command": "/full/path/to/shellwise",
            "args": ["hook", "claude-code"], "timeout": 5 }
        ]
      }
    ]
  }
}

Switch it off any time with SHELLWISE=off. The same check is a plain CLI (shellwise check, shellwise lint), so any agent or script can call it.

Honest scope

What it is, and what it is not

It is

  • A guard against careless mistakes of an agent that means well
  • A linter for the commands and scripts agents write
  • A teacher: every finding carries a fix the agent can copy
  • Small: one binary, no service, no network, no telemetry

It is not

  • A security boundary. It catches mistakes, not someone deliberately working around it
  • A permission system. It does not decide which tools an agent may use
  • A replacement for backups, version control or reading the diff
  • Finished. This is an early version; known gaps are listed in the README
